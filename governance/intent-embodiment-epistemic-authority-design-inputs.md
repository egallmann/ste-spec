# Intent, Embodiment, and Epistemic Authority — Design Inputs

## Status and non-authority notice

**NON-NORMATIVE DESIGN INPUTS — This artifact records current authority, contradictions, evidence, and open questions. It does not establish architectural truth and MUST NOT be treated as an ADR, contract, invariant, or accepted design decision.**

Status: design input only. This is not an ADR, does not change the Architecture IR, and does not allocate authority. It records the current source state for a subsequent, explicitly governed design decision.

## Executive findings

1. Current accepted `ste-spec` doctrine separates declared documentation-state, integration-state, runtime factual evidence, contracts, and admission/governance; it does not yet provide one shared epistemic vocabulary across those surfaces.
2. Runtime authority is intentionally external: it reconstructs observed embodiment and bounded coverage, while `ste-spec` assigns Runtime factual-evidence production and keeps caller-facing admission outside Runtime.
3. The strongest source tension is terminology, not an accepted-ADR conflict. Several orientation surfaces use documentation-state as "current truth" or say undocumented state is nonexistent, while the glossary more narrowly defines it as what the organization has declared.
4. Negative claims have a materially stronger external formulation: Runtime treats absence as a versioned, coverage-bounded predicate result, not an extractor default. `ste-spec` has explicit-unknown and provenance doctrine but no governed crosswalk to that formulation.
5. Linkage-surface mechanics expose confidence, freshness, and negative-space fields, but do not map them to Runtime support bases, coverage, or bounded absence. This is a contract-alignment question, not evidence that either authority is wrong.
6. A design journal is appropriate only after resolving the word "ADR" and deciding whether a cross-authority epistemic vocabulary is desired. No proposed ADR in this package supplies that decision today.

| Fault line | Current source-grounded finding | Authority consequence |
|---|---|---|

| Intent vs embodiment | ADR-L-0031/0041 and current component/IR doctrine distinguish intent/evidence/admission roles, while Runtime ADR-L-0002/0003 explicitly separates project intent from Runtime embodiment. The conflating `ste-spec` surface is the unqualified documentation-state-as-what-exists/current-truth wording, not an accepted ADR. | The seam exists but has no accepted `ste-spec` mapping contract or canonical vocabulary. |
| Unknown vs absent | ADR-L-0006 defines extraction unknowns. Current `ste-spec` has no accepted coverage-qualified absence semantics; IR gap prose also uses “declared absence.” Runtime ADR-L-0006 separately defines unobserved, unsupported, excluded, and absent. | Unknown and absent cannot be projected into each other under current authority. |
| Evidence vs inference | ADR-L-0031 defines factual Runtime evidence; IR doctrine defines explicit/derived/heuristic provenance; ADR-L-0001 forbids guessed extraction edges; the Architecture RECON diagram still says “Infer invariants.” | Evidence, derivation, heuristic provenance, and inferred support overlap lexically but lack governed equivalence. |

## Current authoritative model

The accepted `ste-spec` model is a multi-surface authority model, not a single undifferentiated truth store:

| Surface | Current authority statement | Epistemic consequence |
|---|---|---|
| Accepted logical ADRs | Normative architecture decisions for this repository | Establish accepted decisions, subject to their stated scope. |
| Documentation-state | The declared, machine-readable repository substrate | It records what the organization has declared; it is not proof that all physical embodiment is observed. |
| Architecture IR | Semantic ontology authority in its architecture document; mechanical pins in contracts | Semantic and mechanical authority are deliberately split. |
| Contracts and invariants | `ste-spec` owns contract shape and invariant/rule expression | Consumer-local prose and types cannot supersede them. |
| Runtime evidence | Runtime produces factual evidence; caller-facing admission remains outside Runtime | Evidence is not an admission or execution-eligibility decision. |
| Derived documentation and reports | Generated or reporting surfaces | Committing or publishing a derived artifact does not make it authoritative. |

The package uses the terms **declared**, **observed**, **reconstructed**, **derived**, **asserted**, **unknown**, **supported**, **covered**, and **admitted** descriptively. Their cross-surface meanings are not yet governed as a single vocabulary.

## Gaps in evidence

- No accepted `ste-spec` source examined defines a cross-authority mapping to Runtime's declared/observed/inferred support bases, corroboration, coverage, or bounded absence.
- No field-level mapping was found from linkage-surface `confidence`, `freshness`, or `negative_space` mechanics to Runtime observation-contract semantics.
- No accepted source was found that states whether documentation-state's "truth" language is intentionally declarative, observational, or both.
- No accepted mapping was found between ADR-L-0028's Fabric “canonical state” scope and successor Runtime-owned embodiment state; resolving Fabric/Gateway disposition is outside this slice.
- No accepted terminology decision was found that reconciles the glossary's "converged, binding" ADR definition with proposed logical ADRs.
- No accepted taxonomy was found that establishes exact equivalence or hierarchy among constraint, invariant, and rule.
- This package did not evaluate implementation behavior, generated outputs, or external repository history beyond the identified external authority inputs; it therefore makes no claim about runtime conformance or historical completeness.
